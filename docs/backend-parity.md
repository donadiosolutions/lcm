# SQLite and PostgreSQL surface parity

LCM chooses a storage backend for its configured home and daemon at startup.
SQLite is the default. A home configured for PostgreSQL uses that database for
durable project storage, with verified TLS, a registered machine, and a binding
from each selected local project to its remote identity. A connection failure,
missing binding, or refused publication stops the operation. It does not switch
the project to SQLite. Use separate configured homes and daemons when comparing
backends; there is no per-project backend selector or live backend switch.

The [command-line guide](cli.md) describes the supported commands and recovery
messages. This page explains the scope and evidence of the backend parity tests.
A checked-in inventory describes the intended coverage. Only a complete,
successful execution certifies that inventory on a particular source revision.

## What the matrix covers

[`test/surface-parity/surface-matrix.json`](../test/surface-parity/surface-matrix.json)
is generated from the actual CLI command tree, sensitive-command dispatcher,
daemon route registrations, MCP tool definitions, native import providers, and
canonical transfer exports and domains. Every row names one owner scenario and
the assertions that must execute. Registration changes require an explicit
inventory update; normal tests and CI check the generated bytes without updating
them. A new command cannot pass merely because an older command has a similar
name or shares its handler.

The matrix uses these expectation classes:

| Class | Meaning |
| --- | --- |
| `shared-data` | Both backends must satisfy the same semantic assertions on actual durable storage. |
| `backend-independent-control` | Both configured contexts execute the same CLI/control contract. External installers, services, and provider launches use deterministic test doubles. |
| `architecture-specific` | The matrix records why the outcomes differ and checks the actual counterpart result or refusal. |
| `grammar` | The public command grammar, help, or default dispatch is checked in both configured contexts. |

Control tests own root grammar and the 19 setup, service, configuration, connector,
MCP-launch, help, and group commands named by the inventory. Data workers own the
other 40 CLI commands, including identity, events, diagnostics, hooks, and
sensitive-memory operations. Setup calls do not create another completion result
for a row owned by another scenario. Backend independence is an expectation to
test, rather than permission to omit execution.

The data comparison uses two independent processes, each with its own home,
configuration, project roots, daemon, token, and temporary files. It exercises
the built CLI, real daemon routes, and initialized MCP client/server protocol.
It checks returned content, result membership and ordering, errors, durable
effects, project isolation, imports, compaction, promotion, diagnostics, and
capability boundaries. Only specified fixture identities, timestamps, owned
paths, process/port identifiers, and diagnostic timing may be normalized.
Semantic differences, error categories, counts, and provenance remain observable.

Compact-preview, fault-recovery, and direct daemon-readiness checks separately verify that native schema,
logical rows, journal mode, file authority, metadata, and configuration remain
unchanged. SQLite may still change its physical page layout or perform WAL/SHM
bookkeeping during those operations. The data certificate can record these
observed facts as bounded phase, artifact-kind, scope, and count tuples after the
native and authority assertions pass. The artifact expands their fixed names and
reason; it contains no database paths or raw bytes. PostgreSQL certificates
cannot claim project SQLite bookkeeping, though the local hook outbox remains
an explicit scope. These supplementary facts are bound into the producer digest
and do not replace shared semantic comparisons or the stricter diagnostic
immutability checks below.

## Deliberate capability differences

PostgreSQL full-text grep snippets contain normalized search text: case and
accents can differ from the stored message. SQLite full-text snippets retain
source spelling. The tests assert both actual snippet forms while preserving
shared message membership and ordering. They separately verify exact canonical
Unicode through native readback and regex results, as described in the
[PostgreSQL search contract](../src/storage/postgresql/reference/postgresql-search.md).

PostgreSQL machine registration and remote project bindings are authority
requirements. SQLite's local project identity is not a substitute for a
registered PostgreSQL UUID. Commands whose operation requires PostgreSQL must
produce their documented refusal in a SQLite-configured home.

Promotion checks use a fresh project and an ordinary corpus below the configured
deduplication candidate limit. The single passive-event check requires the same
memory and its original provenance to survive reinforcement. This does not
establish exhaustive exact-match recall when other candidates fill the selected
page; that separate workload limit is tracked in
[#1206](https://github.com/donadiosolutions/lcm/issues/1206). The assertions remain
strict if the exercised workload fails.

The native hook outbox is local even when durable project storage uses
PostgreSQL. Its named local event files are permitted by the architecture. A
project `db.sqlite`, WAL, or SHM file created as a database fallback is not.
Canonical transfer archives and temporary indexes are also separately named
transfer artifacts, outside project database paths.

Diagnostic reads report the selected backend's actual capabilities. Pool
statistics may have different shapes, but failures remain sanitized and bounded.
PostgreSQL statistics metrics contain aggregate counters and omit
per-conversation details. SQLite statistics include conversation details, whose
identifiers are checked against native storage. The tests assert the actual
field absence or detail membership and the corresponding rendered capability,
while checking the common aggregate counters against each native database.
Admitted project and machine identities remain part of the separate backend
diagnostic snapshot.
Reading diagnostics does not authorize orphan pruning, repair, or deletion.
For an authenticated existing SQLite database, a read may create its necessary
`-wal` or `-shm` read-coordination artifacts, as described in the
[diagnostic contract](cli.md). The parity checks observe this engine bookkeeping
only at the exact owned database's WAL/SHM paths; it is not a general filesystem
exclusion. Durable database bytes and rows, project metadata, configuration, and
the project map must remain unchanged. A diagnostic must not create a missing
database, checkpoint, change journal mode, repair storage, or delete sidecars.
If a safe read requires durable content changes, it reports `unavailable`.
The authenticated direct `GET /health` request is an active readiness operation.
Its separate `health-readiness` bookkeeping phase requires the exact daemon
health row's `effects` assertion and the same native and authority invariants.
It does not relax the observational contracts for CLI `stats`, `status`, or
`doctor`, MCP statistics, or their shared diagnostic snapshot. Those operations
cannot use a readiness receipt to permit sidecar removal or identity changes.
The separately inventoried authenticated `GET /health/observe` endpoint reports
process identity with storage status `unverified`. It supports diagnostic
identity checks without probing active storage readiness. Its assertions require
authentication, stable identity, and the strict read-only contract; it cannot
use the active-health bookkeeping allowance or certify storage readiness.
Failure scenarios check unavailable or exhausted storage, cancellation, cleanup,
and recovery of the same configured service. Test timing bounds are fixture
assertions, not a production latency guarantee.

There are three distinct transfer contracts:

| Operation | Scope |
| --- | --- |
| Native session import | Claude and Codex session formats; `all` dispatches to the supported providers. |
| `lcm export` / `lcm import-knowledge` | Version-1 promoted-knowledge JSON, including privacy scrubbing and dry-run behavior. |
| Canonical storage transfer API | Complete backend archive transfer, including all 22 populated record domains and native database readback checks. |

Canonical evidence requires SQLite → SQLite, SQLite → PostgreSQL, PostgreSQL →
SQLite, and PostgreSQL → PostgreSQL in each PostgreSQL CI leg. Backend-specific
constructor rows declare their applicable directions. Every domain must pass in
all four directions. These library APIs do not add a canonical-transfer CLI or
HTTP endpoint.

PostgreSQL transfer resume requires the same live source snapshot. Opening a
new PostgreSQL source produces a new manifest and cannot resume a destination
bound to the previous manifest; that mismatch is explicitly refused. This
evidence does not establish resume across a PostgreSQL source process restart.

Runtime certification has additional limits. A strict TypeScript consumer of
the emitted declarations can require `@types/pg`, which
the package does not currently declare; runtime package smoke tests do not
certify declaration portability ([#1176](https://github.com/donadiosolutions/lcm/issues/1176)).
The fixed-scalar materialization bound for malformed owned transfer-ledger rows
was fixed upstream in [#1212](https://github.com/donadiosolutions/lcm/pull/1212),
closing [#1140](https://github.com/donadiosolutions/lcm/issues/1140). This is
historical fix provenance: ordinary canonical transfer and native readback
assertions do not independently certify that malformed-input resource bound.
The repository also has a separately tracked test-adapter typing gap
([#1205](https://github.com/donadiosolutions/lcm/issues/1205)). Runtime evidence
and the production typecheck do not certify every test adapter's TypeScript
annotations.

## Read a run's evidence

Each of the two PostgreSQL 18 CI jobs independently runs the complete SQLite and
PostgreSQL comparison, fresh control tests, and all four canonical directions.
The jobs upload separate artifacts named
`surface-parity-<run-id>-<attempt>-<leg>`. Both must pass. Results from two
incomplete jobs cannot be combined into one complete result.

Each artifact contains:

| File | Interpretation |
| --- | --- |
| `surface-matrix.json` | The exact inventory used by that run. |
| `results.json` | Expanded producer/backend/direction results, executed assertion IDs, verdicts, cleanup, and normalized-result digests. |
| `provenance.json` | Tested checkout SHA, candidate SHA when available, source-content binding, command, pinned container images, runtime observations and actual PostgreSQL corpus counts, CI identity, and output budgets. |
| `regressions.json` | Inventory regression references and their execution status. An upstream issue or source reference alone is historical provenance, not a fresh passing assertion. |
| `SHA256SUMS` | SHA-256 digests for the four JSON files; the checksum file does not hash itself. |

A pull-request job may test GitHub's temporary merge commit. Its `testedSha`
therefore can differ from the pull request's `candidateSha`; both identities are
recorded. Certificates also bind the source and test file contents, including
SQL and fixture scripts. That content binding works within the existing
read-only container mount without relying on a host-only Git worktree path.

Local runs may include uncommitted work. `workingTreeClean` checks tracked changes
and untracked files while respecting Git ignore rules. When it is `false`,
`testedShaMeaning` is `base-checkout-metadata`: `testedSha` identifies the base
checkout, while `sourceContentDigest` binds the actual tested source contents.
The artifact includes no changed filenames or raw diff. Release acceptance still
requires the clean reviewed candidate and its fresh CI evidence.

Test producers emit indexed `LCM_SURFACE_PARITY_V1` certificates through the
existing sanitized output. Full semantics are compared before emission; the
certificate records completion bits and digests, without queries, payloads,
credentials, connection strings, home paths, raw errors, or certificates. The
extractor expands the indexes against the exact matrix hash. Missing or duplicate
producers, rows, or assertions, unknown bits, failed cleanup, altered source,
mixed harness run identities, and failed assertions prevent certification.

The total added certificate budget is 8,192 bytes per complete run. The existing
65,536-byte capture cap per harness stream remains unchanged. Truncation,
sanitizer damage, or an exceeded cap is an evidence failure, not a backend parity
verdict. A failed artifact can preserve incomplete results for diagnosis; its
`complete: false` cannot satisfy the gate. Harness test failures remain failures
even when extraction or upload succeeds.

## Reproduce or update the inventory

Bootstrap the pinned package manager as documented in
[Development](development.md), then install the locked dependencies. To check
the inventory and its immediate evidence boundaries:

```bash
pnpm install --frozen-lockfile
pnpm exec vitest run test/daemon/routes/surface-parity-inventory.test.ts \
  test/surface-parity/control-parity.test.ts \
  test/surface-parity/assertions.test.ts \
  test/scripts/surface-parity-artifact.test.ts
```

After deliberately changing a supported registration and its scenario/assertion
mapping, regenerate and then review the matrix diff:

```bash
pnpm run test:surface-parity:inventory
pnpm exec vitest run test/daemon/routes/surface-parity-inventory.test.ts
```

Run the existing full PostgreSQL harness against its disposable database using
its pinned CI container path. Setting `GITHUB_ACTIONS=true` on this command
selects that existing path locally: the built CLI and MCP launch their actual
packaged foreground daemon without depending on the host's user service manager.
This is the parity reproduction path; a host-mode harness result does not
establish that container-path claim. Use a private output directory outside the
checkout and preserve the harness status:

```bash
parity_output="$(mktemp -d)"
set -o pipefail
GITHUB_ACTIONS=true pnpm run test:postgresql 2>&1 | tee "$parity_output/harness.log"
parity_harness_status=${PIPESTATUS[0]}
node scripts/surface-parity-artifact.mjs \
  "$parity_output/harness.log" "$parity_output/evidence"
parity_evidence_status=$?
test "$parity_harness_status" -eq 0 && test "$parity_evidence_status" -eq 0
```

The harness owns its credentials, database, containers, temporary roots, and
cleanup. It uses neither the globally installed LCM nor a user's database or
daemon. Core CI independently enforces the complete production coverage gate.
Inventory, focused tests, or a prior passing revision do not replace that fresh
coverage run or either complete PostgreSQL job.

If a run fails, inspect its fixed assertion IDs and incomplete producer list,
then reproduce the affected public operation in a disposable configured home.
For a missing binding, use the documented project create/link workflow. For a
storage or TLS refusal, correct the configured authority or connection and retry
the selected backend. Do not delete local metadata or switch backends as an
implicit repair. Known upstream regressions remain failures when reproduced;
their historical fixes do not waive an assertion on the tested revision.
