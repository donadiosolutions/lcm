# Issue #615 PostgreSQL Project Storage Factory Implementation Plan

> **For implementation workers:** use `superpowers:subagent-driven-development`. Follow this plan task by task, write the public-seam test first, and do not recursively invoke the MoM workflow.

**Goal:** Deliver the production PostgreSQL `StorageBackendFactory` composition root and complete project-scoped `ProjectStorage`, while keeping normal daemon/CLI routing staged for #617-#619.

**Architecture:** Add one eager async seam, `createPostgreSqlStorageBackendFactory(config)`, that creates exactly one `PostgreSqlRuntime`, proves verified connection and complete read-only runtime readiness, and then returns a concrete factory. The factory reuses a caller-supplied live backend-publication token or performs two short authenticated consumer-lock snapshots around tokenless PostgreSQL work. Each authenticated project operation verifies the explicit PostgreSQL project/machine/path binding inside the existing project-scoped guarded PostgreSQL transaction before returning a `PostgreSqlProjectStorage` facade over every parity repository. The existing synchronous generic selector and staged unavailable error remain unchanged until their owning routing issues.

**Tech stack:** TypeScript 6.0, Node.js 22+, `pg` 8.22.0, Vitest 4.1.10, PostgreSQL 18 harness. No new dependency.

## Scope and non-negotiable boundaries

- This branch and PR close only issue #615. Do not absorb #616-#620. Merge and run the canonical Codex resync before creating the next issue branch.
- SQLite stays the default. `createPostgreSqlStorageBackendFactory` accepts only the resolved `backend: "postgresql"` branch; there is no PostgreSQL-to-SQLite fallback.
- Keep `createStorageBackendFactory`, `UnavailablePostgreSqlStorageBackendFactory`, `StorageBackendUnavailableError`, `selectStorageBackend`, and the staged daemon 503 contract intact. #617 owns normal daemon/MCP/compaction/retrieval selection, #618 owns CLI/import/export, and #619 owns stats/doctor.
- The staged `StorageBackendUnavailableError` wording therefore remains intentionally outdated on this #615 branch; #617 removes that normal-route boundary and its message when it selects the real async factory.
- Construction requires no publication token. `projectExists`, `openExistingProject`, and `openProject` require authenticated local publication admission. With a caller-supplied live `BackendPublicationLockToken`, call `assertStorageBackendPublication({ backend: "postgresql", homeDir }, token)` before and after the remote batch while the caller retains the lock. Without a supplied token, call `withStorageBackendConsumerLockAsync` twice with short synchronous callbacks: each callback asserts the PostgreSQL selection using its live token and captures `readBackendPublicationJournal()` plus `captureBackendPublicationState()`. Release the first local lock before PostgreSQL I/O and require the second authenticated journal checksum/phase/backend and complete config/project-map witnesses to equal the first before returning. The underlying private mutation lock does not wait: contention rejects, so there is no factory-owned publication waiter to cancel. PostgreSQL's existing project mutation guard adds a shared per-project advisory lock and rejects an unresolved `lcm.fenced_leases` publication row during the database batch; it is a remote unresolved-publication fence check, not a substitute for authenticated local publication evidence.
- Preserve the existing `StorageBackendFactory` method signatures. Do not append a positional signal argument or modify SQLite. Cancellation is provided by the existing bounded PostgreSQL runtime query/transaction signals plus a private abort controller for each project facade and for factory shutdown; no public cancellation API is added in #615. Publication contention is an immediate admitted-operation failure, not a cancellable wait.
- `openProject` does not create or repair remote identity. `lcm project create` and `lcm project link` remain the explicit creation/link authorities. An unbound local project already fails through `StorageIdentityConfigurationError`; an absent or mismatched remote record fails with a sanitized PostgreSQL initialization error. `openExistingProject` returns `null` only when the authenticated remote project record is genuinely absent.
- Extend `StorageIdentityContext` with optional `selectedPath`, populated only by the cwd-aware `projectIdentity(cwd, config, token)` boundary as `resolve(cwd)` after worktree reconciliation and passed explicitly through `resolveStorageIdentityContext`; PostgreSQL factory calls reject a missing selected path. This is the same absolute lexical spelling that `lcm project create` and `lcm project link` preserve through `remotePath(projectPath)`. Never replace it with the local map's canonical path or `resolveGitProjectAnchor(cwd)?.canonical`: those identify the local project family but can differ from the selected symlink, linked worktree, case spelling, or subdirectory that owns the remote alias. This preserves backend-independent `ProjectIdentity` and existing SQLite structural callers.
- PostgreSQL identity verification uses `PostgreSqlIdentityRepository.getProject(projectId)`, not unguarded `resolveProject`. `getProject` sets `projectIds`, so `PostgreSqlRuntime.query` promotes its non-mutating `SELECT` into an admitted `READ COMMITTED, READ WRITE` transaction that takes the shared per-project advisory lock and rejects an unresolved publication fence. The factory filters the returned complete alias list and requires exact lower-case UUIDv7 project and machine IDs, `remoteProjectId === id`, and exactly one alias whose `machineId`, `path === selectedPath`, and `normalizedPath === normalizeProjectPath(selectedPath)` all match. Local publication proof remains independently mandatory before and after that remote check.
- Introduce and export `ResolvedPostgreSqlConfig = Extract<ResolvedStorageConfig, { backend: "postgresql" }>` from `src/daemon/config.ts`; it is the exact issue-defined constructor input and includes the resolved `migrationRole` below.
- The explicit, non-secret `storage.postgresql.migrationRole` is the trusted schema-owner authority. Model defaults as `Omit<PostgreSqlStorageSettings, "migrationRole">`, add `migrationRole?: string` only to the stored settings, and omit it from `DEFAULT_POSTGRESQL_STORAGE_SETTINGS` because no role can be inferred safely. In the PostgreSQL branch, resolve the already merged stored/invocation override first and use `LCM_POSTGRES_MIGRATION_ROLE` only as a fallback (`postgresql.migrationRole ?? env.LCM_POSTGRES_MIGRATION_ROLE`); return it as required in `ResolvedPostgreSqlConfig`. SQLite resolution neither validates nor persists it. Validate it as a bounded printable PostgreSQL role identifier, and make `daemonConfigForPersistence` explicitly whitelist the five non-secret PostgreSQL settings—`poolMax`, `connectionTimeoutMs`, `idleTimeoutMs`, `statementTimeoutMs`, and the effective `migrationRole`—while continuing to omit `url` and `caFile`. Consequently an environment-derived role becomes durable on the next config write and round-trips without that environment. Add it to the managed child allowlist as `LCM_POSTGRES_MIGRATION_ROLE`; an environment-supplied role participates in the existing launch digest, while a persisted-only role is read from config and needs no child environment entry. Never infer it from `MigrationStorageWitness.identitySha256` or catalog ownership. #621 deliberately keeps that witness opaque.
- TLS peer verification is established by the existing resolved CA/client-config path (`rejectUnauthorized: true` and hostname `checkServerIdentity`) plus a successful live connection. `pg_stat_ssl.ssl` proves encryption only. Eager construction requires a strictly `healthy` runtime result; `degraded` and `unavailable` both fail construction and close the pool.
- Runtime readiness is read-only and fail-closed: exact ordered packaged migration history; configured migration-role ownership of schema, ledger, and every managed object; schema ACL; latest definition, relation/column ACL, and identity-function fingerprints; PostgreSQL 18/UTF8/UTC; required extensions and search configuration; exact required current-role privileges for all nine repositories; no DDL, migration lock, migration writes, ownership changes, or automatic grant changes. PostgreSQL system catalogs are metadata-readable under the supported PG18 contract; integration tests prove the restricted runtime sees the exact managed inventory through `pg_catalog` without extra base-table privileges.
- Add a dedicated reviewed `postgresql-runtime-readiness-grants.sql`: exact `SELECT` on `lcm.schema_migrations`, `USAGE` on `public`, and `EXECUTE` on both `public.digest(text, text)` and `public.digest(bytea, text)`. Fingerprint groups aggregate text; search-configuration readiness passes `convert_to(...)` bytea. Extend schema-snapshot ACL normalization for sanctioned non-owner ledger `SELECT`. Every released snapshot inherits one complete current ACL inventory, so replace the baseline relation-ACL hash from which all four snapshot entries inherit, using a freshly migrated PostgreSQL 18 database with the complete reviewed runtime grant set. Runtime mode supplies the configured expected owner to the extracted verifier; it never trusts an owner discovered from the same catalog being verified.

Required entries are the direct non-grantable owner-granted privileges from readiness, identity, conversation, summary/context, memory, search, and coordination scripts. Native-transcript persistence is outside `ProjectStorage`, so transcript-script entries are the only sanctioned optional set. Passive-event persistence is also outside the `ProjectStorage` interface, but it has no separate grant script: the required coordination grant script owns its shared tables/functions as well as the exposed coordination repository. Tests parse every reviewed script and prove the manifest neither omits nor invents an entry.

- Runtime authority policy is exact: require `SESSION_USER = CURRENT_USER =` the URL username; runtime role differs from `migrationRole`; runtime role is not superuser, database/schema/object owner, `CREATEROLE`, `CREATEDB`, replication, or `BYPASSRLS`; and it has no direct or transitive role memberships.
